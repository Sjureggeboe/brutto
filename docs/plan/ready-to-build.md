## 0. The ten things to know first

1. **M0 does not need Digdir, Maskinporten or any scope.** If the a-melding is uploaded by hand (F-MYN-14, as the JSON the API takes; see A11) and tax cards are ordered through Skatteetaten's tax-card file service (B5), M0 depends on none of the authority onboarding. M0 is blocked by these things instead:
   - which legal entity runs the payroll, and its facts (D2)
   - the current system's 2026 export, at line level and not only PDFs
   - people who hold the Altinn 3 access packages for that entity: **A-ordningen** for the a-melding upload and the A07 download, and **Lønn** for tax cards (A-ordningen does not cover tax cards). Check this week (item 6)
   - our own trekk implementation, tested against Skatteetaten's table file
   - the bank accepting pain.001
   - the accounting import format
   - hosting in Norway
   - Sjur as the payroll authority ("fasit")
2. **F-MYN-14 (export for manual upload) is tagged `"mvp": "Etter MVP"` in `analyse/build/data/omr-K4.json`, but M0 depends on it.** Move it to M0 (done in `docs/plan/scope.csv`).
3. **The licence for the trekkrutine (F-TRK-07, the tax withholding routine) does not block M0 or M1.**
   - The repo still has no licence. The GitHub API showed `license: null` on 29.10.2026, and the last push was 9.12.2025.
   - The tables, rates and the algorithm as a rule are almost certainly free to use (åndsverkloven § 14, N13 §1.1, needs legal confirmation).
   - Write our own Rust port (about 150 lines, `f64` in the same order of operations as the Java) and require 100 % match against the published table file. Ask for a licence in parallel, but don't wait for it.
4. **The vendor company and its orgnr (M02) is the root of the M1 critical path.** The orgnr becomes part of the Altinn system ID (`<orgnr>_brutto`). Changing it later means every customer must approve a new system user (N06 §9). `PLAN.md` D3 puts it in this week's decisions.
5. **Two estimates for the onboarding time disagree.**
   - N06 (29.10.2026): 7–10 weeks from orgnr to the first production call, best case `[verify]`.
   - CLAUDE.md, B19 and F-MYN-01: 3–5 months.
   - Plan M1 on about 3 months (`PLAN.md` §2.3). The Altinn II cut-over (17.11 and 31.12.2026) and the 2027 tax-card season probably make the Nov–Dec queues long (N06 §5).
6. **Two Skatteetaten pages disagree on when old Altinn II roles stop working for the a-melding.**
   - One says submission with old roles ends on 17 November 2026.
   - The page for upload as file says the roles work until the end of 2026.
   - Plan on 17.11.2026 for anything sent with old roles. That matters for the current system, which submits 2026-11 (due 7.12.2026) and 2026-12 (due 5.1.2027): **confirm this week that its submission channel still works after 17.11.2026** (`PLAN.md` §1.1, §2.4 item 3). For Brutto, the first live upload is period 2027-01 at the earliest (deadline 5.2.2027), and the uploader's A-ordningen package must be confirmed before then.
7. **Decide which system is the sender of record for November and December 2026 (B19, B16, D-27).** If Brutto sends any 2026 month, Brutto also owns these:
   - the year-to-date (YTD) import for January–October
   - a 2026 annual summary (sammenstillingsoppgave) by 31.1.2027
   - holiday-pay (feriepenger) bases
   - continuity of the employment IDs (arbeidsforhold-ID)

   Recommendation: run November and December as shadow runs and compare them to the øre (December tests halvt trekk, the half tax deduction). Go live from January 2027, which gives a clean income year. **Decided in `PLAN.md` (D1, new B44):** the current system submits all of income year 2026. Brutto shadow-runs November and December and is system of record from period 2027-01 if both shadows are clean by 15.1.2027 (stretch, ≈40 %), otherwise 2027-02 (the planning date, ≈65 %) or 2027-03 at the latest. B19 is reworded to match (`PLAN.md` §8); Sjur signs.
8. **Payroll knowledge is the real bottleneck, not code (R3 strategy §2.3).**
   - Name Sjur as the payroll authority under B28 (veto), with a deputy.
   - **Decided in `PLAN.md` (D4):** contract an external payroll expert now, from November 2026: 20–30 h for M0 (countersigning golden cases) and 100–150 h before M1. The expert is also the B28 deputy. This paper first proposed buying the hours for M1 only.
   - Before M0 goes live, the main external check is still the old payroll system: a parallel run to the øre.
9. **Legal work can go to one lawyer as a single assignment** (morgen.md question 2). Only a small part of it is needed before M0: a DPA if the vendor company and the M0 employer are different entities, and the regnskapsførerloven boundary. The rest blocks M1.
10. **The Tripletex and PowerOffice API terms (N40) block only an accounting adapter in M1, and the adapter is pilot-pulled:** it is built only if a signed pilot needs it, chosen at G4 (31.3.2027). M0 and every M1 customer can use a voucher file the customer imports (F-REG-17).
