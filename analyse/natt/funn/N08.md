## Kort svar

Rust dekker nesten alt fase 1 trenger med modne og aktivt vedlikeholdte crates: tokio, reqwest, axum, sqlx 0.9, rust_decimal 1.43, quick-xml, calamine, typst 0.15 og wiremock/httpmock. Det finnes ingen Maskinporten- eller Altinn-klient i Rust (0 treff på crates.io, ett forlatt GitHub-repo fra 2022). Ingen JWT-crate kan signere asynkront med en nøkkel i KMS. Brutto må derfor skrive en liten JWS-bygger med en egen `Signer`-trait for AWS KMS, Azure Key Vault eller GCP KMS. Anbefalingen er:
- Generer modellene med typify eller progenitor, med egne typer for beløp og tidspunkter, og håndskriv lesestien.
- Bruk sqlx med RLS gjennom en egen `TenantTx`-type.
- Lag en egen Postgres-kø med én aktiv jobb per opplysningspliktig og en felles token-bøtte.
- Bruk Typst for PDF/A.

To fallgruver må låses fra dag én. `Decimal::round()` og `round_dp()` bruker bankers avrunding. Og Tripletex har 2 096 beløpsfelt som er `number` uten format, så de blir `f64` hvis vi ikke erstatter typen. Hullene Brutto må fylle selv er Maskinporten og Altinn, konvoluttkryptering med blind indeks, et bitemporalt repolag, jobbkø med samtidighetsnøkkel, opptak med vask, en SAF-T-leser (1.40 er obligatorisk fra 1.1.2027), import av Skatteetatens regneark og XSD-validering (det finnes ingen moden validator skrevet i ren Rust).

### 1. Maskinporten og OAuth2 JWT-grant

**Protokollen (Digdir):**
- Maskinporten støtter `RS256`, `RS384` og `RS512`. Headeren må ha `kid` eller `x5c`, ikke begge.
- `exp − iat` kan være maks 180 sekunder, og 120 er anbefalt. N06 skriver «≤ 120 s». Det er innenfor kravet, men grensen er 180.
- `grant_type` er `urn:ietf:params:oauth:grant-type:jwt-bearer`, sendt som `application/x-www-form-urlencoded` med `assertion`. Klientautentisering trengs ikke.
- Levetiden på tokenet er ikke dokumentert. Eksempelet viser `expires_in: 599`.

**Finnes det en ferdig klient?**
- crates.io: 0 treff på `maskinporten`, `altinn`, `digdir`, `idporten`, `a-melding`, `tripletex` (bare en CLI med versjon 0.0.0) og `fiken`.
- GitHub: Det eneste Rust-repoet er `kometen/enc_token` (2022, 0 stjerner).
- Referanseklienter i andre språk kan brukes som fasit for flyten:
  - `Altinn/altinn-apiclient-maskinporten` (.NET)
  - `ks-no/fiks-maskinporten` (Kotlin/Java)
  - `felleslosninger/jwt-grant-generator` (Java)
  - `nais/digdirator` (Go)
- **Brutto må skrive klienten selv.**

**Token-cache:**
- Bruk `moka` 0.12.16 (`future::Cache`) med `Expiry` per oppføring og `try_get_with`. Da blir samtidige forespørsler etter samme token til ett kall mot Maskinporten.
- Nøkkelen er (miljø, scope, `systemuser_org`, `externalRef`), som i N06.
- Forny ved `expires_in` − 60 s [forslag].
- Lagre token som `secrecy::SecretString`, og logg det aldri. Logg `jti`, `kid`, scope og orgnr.

**Skisse (ca. 60 linjer i ekte kode) [forslag]:**

```rust
#[async_trait::async_trait] // eller nativ async fn + enum-dispatch, se §9
pub trait Rs256Signer: Send + Sync {
    fn kid(&self) -> &str;
    async fn sign_sha256_digest(&self, digest: [u8; 32]) -> Result<Vec<u8>, SignerFeil>;
}

let signing_input = format!("{}.{}", b64url(&header_json), b64url(&claims_json)); // aud, iss, scope, iat, exp=iat+120, jti=uuid
let digest: [u8; 32] = Sha256::digest(signing_input.as_bytes()).into();
let sig = signer.sign_sha256_digest(digest).await?;     // KMS: AWS, Azure, GCP eller lokal PEM i dev
let assertion = format!("{signing_input}.{}", b64url(&sig));
// POST {issuer}/token: grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer&assertion=...
```

- Bruk `reqwest-retry` 0.9 for 5xx og tidsavbrudd.
- Prøv ikke på nytt ved `invalid_grant`, med ett unntak: klokkeforskjell. Logg `iat` og serverens `Date`.
- En test signerer med en lokal nøkkel og verifiserer med `jsonwebtoken` mot JWK-en. Kontrakttesten mot `test.maskinporten.no` kjøres om natten (N39 L2).

**Anbefaling (N04 bekreftet: generer modellene, håndskriv lesestien):**
1. Et lite skript plukker ut skjemaene de håndskrevne kallene trenger, ved å følge `$ref`-ene.
2. Kjør `cargo-typify`. Bruk progenitor bare hvis vi vil ha de genererte kallene. Sjekk inn koden i en egen crate per system, for eksempel `brutto-ext-tripletex-modell`.
   - Bruk **ikke** `build.rs`.
   - Da får vi en lesbar diff ved ny API-versjon og raskere bygg, og kodeagenter ser koden.
3. Konverteringer:
   - `number` → `Decimal`
   - `Beloep` → `Beloep`
   - `BeloepSomHeltall` → `HeleKroner`
   - `Desimaltall` → `Sats`
   - `DatoKlokkeslett` → `SkattTidspunkt` (godtar tidspunkter med og uten sone)
4. Skatteetaten: Generer alle 96 skjemaene. Håndskriv de tre kallene (bestill, poll og hent) med logikk for 429 og `KLAR` (N03, M06).
5. Tolerant lesing:
   - Ikke bruk `deny_unknown_fields`.
   - Alle felt er `Option` med `#[serde(default)]`.
   - Fang ukjente felt med `serde_ignored` 0.1.14 og meld dem til F-MYN-24. Da oppdager vi endringer uten nytt versjonsnummer, som 12.10.2026.
   - Bruk `serde_path_to_error` for å få feilstien.

### 3. Desimaler og avrunding

**`rust_decimal` 1.43.0 (MIT, 1 342 stjerner):**
- 96-bits mantisse og ca. 28 signifikante sifre.
- Standard-serde godtar både tekst og tall. **JSON-tall går via `f64`.** Kildekoden viser `visit_f64` → `Decimal::from_str(&value.to_string())`. Rust skriver korteste representasjon som gir samme `f64` tilbake. Tall med ≤ 15 signifikante sifre blir derfor eksakte, mens lengre tall avrundes uten feilmelding.
- Med serde_json-featuren `arbitrary_precision` leser `rust_decimal::serde::arbitrary_precision` tallet som tekst, og verdien blir eksakt. Featuren aktiveres med `serde-with-arbitrary-precision`.
- Kostnadene ved `arbitrary_precision`:
  - Featuren gjelder hele bygget fordi Cargo slår sammen features.
  - Den endrer `serde_json::Value::Number`.
  - Tall som bufres gjennom `#[serde(flatten)]` eller `untagged`-enum, kommer som det interne kartet `$serde_json::private::Number`, og det har gitt feil i praksis.
  - README advarer om at featuren serialiserer som tall som ligner flyttall.
  - Tripletex-spesifikasjonen har ingen `oneOf` eller `anyOf`, så typify lager trolig få `untagged`-enumer [verifiseres].

| Kilde | Format | Parsing i Brutto |
|---|---|---|
| Skatteetaten `Beloep` | Tekst | `Decimal::from_str_exact` (feiler i stedet for å avrunde) |
| Skatteetaten `BeloepSomHeltall` | Tekst, hele kroner | Newtype som avviser desimaler |
| Skatteetaten `Desimaltall` | Tekst, maks 12 + 5 sifre | `Sats` med validering mot mønsteret |
| Tripletex, PowerOffice og ReAi | JSON-tall | `arbitrary_precision` eller f64-stien med grense på 15 sifre (spørsmål til Peter og Sander) |
| Fiken | Øre som heltall | `Decimal::new(ore, 2)` fra `i64` |
| SAF-T 1.30 `Amount` | `xs:decimal`, 18 sifre og 2 desimaler | `Decimal` |
| SAF-T 1.40 `CurrencyAmount` og `ExchangeRate` | `SAFlongmonetaryType`: **38 sifre og 18 desimaler** | **Mer enn rust_decimal klarer.** Behold som tekst eller `bigdecimal`. Brutto trenger bare `Amount` i NOK. |

**Avrunding (docs.rs, 1.43.0):**
- `round()` og `round_dp()` følger «Bankers Rounding», så 6,5 → 6 og 7,5 → 8. Det er **ikke** kommersiell avrunding.
- `round_dp_with_strategy(dp, RoundingStrategy::MidpointAwayFromZero)` gir kommersiell avrunding (HALF_UP).
- Bekreftede strategier er `MidpointNearestEven`, `MidpointAwayFromZero`, `ToZero` og `AwayFromZero`. Den fullstendige listen [verifiseres].
- Lås dette i `clippy.toml` [forslag]:

```toml
disallowed-methods = [
  { path = "rust_decimal::Decimal::round",    reason = "Bankers. Bruk brutto_penger::avrund(Avrunding)" },
  { path = "rust_decimal::Decimal::round_dp", reason = "Bankers. Bruk brutto_penger::avrund(Avrunding)" },
  { path = "rust_decimal::Decimal::from_f64_retain", reason = "Aldri f64 inn i beløp" },
]
```

- Slå også på `clippy::float_arithmetic` i crate-ene for penger og regler.
- **Avrundingsregler hører hjemme i regelpakken (ADR-06):** strategi, presisjon og nivå (linje, grunnlag eller sum).
- I fase 1 regner Brutto bare AGA som grunnlag × sats per sone og sammenligner med `sumArbeidsgiveravgift` med toleranse (K03, N03).
- Forskuddstrekk er hele kroner i A07. Hvordan prosenttrekk avrundes, [verifiseres] (F §1.10).
- Største-rest-fordeling finnes ikke som crate og må skrives selv.

**Alternativer:**
- `bigdecimal` 0.4.11 har vilkårlig presisjon på heapen. Den trengs bare der 28 sifre ikke holder.
- `fastnum` 0.7.5 er ung og har fast størrelse.

**Grensene ut av Brutto:**
- Postgres `NUMERIC` via sqlx-featuren `rust_decimal` (D05).
- API-et serialiserer med `rust_decimal::serde::str`, så beløp sendes som tekst. JavaScript-tall er `f64`.
- utoipa-featuren `decimal` dokumenterer feltet som streng.

**RLS for flere kunder (D03, F-SIK-11):**

```sql
ALTER TABLE t ENABLE ROW LEVEL SECURITY;
ALTER TABLE t FORCE ROW LEVEL SECURITY;          -- også for eier
CREATE POLICY t_tenant ON t
  USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
  WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
-- Uten innstilling gir current_setting(..., true) NULL og 0 rader. Policyen feiler lukket.
```

- I Rust er `TenantTx` den eneste måten å få en executor på. Den åpner transaksjonen og kjører `select set_config('app.tenant_id', $1, true)`.
  - Svix gjør det samme med `SecureTransaction` via axums `FromRequestParts`.
  - `tenaxum` er en liten crate med samme mønster.
- Applikasjonsrollen eier ikke tabellene og har ikke `BYPASSRLS`.
- Visninger over rådata må ha `security_invoker = true` (PG15+), ellers går RLS tapt. Det er relevant for spørsmål 4 i N03.
- PgBouncer i transaksjonsmodus og sqlx' navngitte prepared statements må testes i den driftsplattformen vi velger [verifiseres].

**Kryptering av fødselsnummer (D09, F-SIK-19, F-SIK-20):**

| Løsning | Vurdering |
|---|---|
| `pgcrypto` | **Frarådes.** Nøkkelen står i SQL-teksten og kan havne i logg og `pg_stat_statements`. Databasen ser klartekst, og KMS kan ikke brukes direkte. |
| Applikasjonsnivå med `aes-gcm` 0.11.1 (RustCrypto, revidert av NCC Group uten vesentlige funn) | **Valgt.** AES-256-GCM med tilfeldig 96-bits nonce og AAD = tenant_id + dataklasse + feltnavn. Én DEK per (tenant, dataklasse), pakket inn av KMS. Kryptografisk makulering ved at DEK slettes. `aws-lc-rs` AEAD er et alternativ. |
| `age` 0.12.1 | For **filer**: eksport, midlertidige SAF-T-filer og backup-uttrekk. Ikke for felt. |
| `aws-esdk` 1.2.4 (AWS Encryption SDK) | Ferdig konvoluttkryptering med KMS-keyrings, men knyttet til AWS og med liten brukerbase |
| `tink-core` 0.3.0 | Uoffisiell port, siste release 11.2024. Frarådes. |

- **Blind indeks:** HMAC-SHA256 (`hmac` 0.13 + `sha2` 0.11) med egen nøkkel per tenant.
  - Bruk en annen nøkkel enn den som krypterer.
  - Normaliser til 11 siffer før HMAC.
  - Fødselsnummer har lav entropi, så indeksnøkkelen må ligge i KMS, aldri i databasen.
- Hold hemmeligheter i `secrecy` og `zeroize`.

**JSONB og krypterte rådata (D07):**
- Kryptert `bytea` kan ikke spørres som JSONB. Anbefaling:
  - Rådata lagres som kryptert `bytea` med SHA-256.
  - Det normaliserte laget ligger i tabeller med RLS.
  - JSONB brukes bare for innhold uten persondata, for eksempel A07 med `utenInntektsmottakere = true` og metadata.
- Det svarer på N03 spørsmål 4.

**Bitemporale tabeller (D08, F §1.4):**
- PG18 har `PRIMARY KEY (…, gyldig WITHOUT OVERLAPS)` og `FOREIGN KEY (…, PERIOD gyldig)`.
  - Uuid-kolonnene krever `btree_gist`.
  - Tomme intervaller avvises.
  - Temporale fremmednøkler støtter bare `NO ACTION`.
- Registreringstid har ingen støtte i Postgres eller i noen crate. Repolaget (`som_kjent(T).gyldig_paa(d)`) må skrives selv.
- Arbeidsforhold-ID lagres som `text COLLATE "C"`. Da skilles store og små bokstaver, og ingenting normaliseres (N36). Temporale fremmednøkler krever deterministisk kollasjon.

```sql

-- Felles token-bøtte (radlåsen gjør oppdateringen atomisk):
UPDATE ratebotte
SET tokens = LEAST(kapasitet, tokens + EXTRACT(EPOCH FROM now() - oppdatert) * rate) - 1,
    oppdatert = now()
WHERE nokkel = $1
  AND LEAST(kapasitet, tokens + EXTRACT(EPOCH FROM now() - oppdatert) * rate) >= 1
RETURNING tokens;
```

### 9. Async-traits og strømmer

- **Status (Rust Project Goals 2026):**
  - `async fn` i trait er stabil siden 1.75, men kan ikke brukes med `dyn Trait`.
  - Det finnes ingen måte å kreve at en implementasjon returnerer en `Send`-future. Return type notation (RTN) venter på den nye trait-løseren.
  - Målet for innebygd dynamisk dispatch er 2026–2027 og er ikke lovet.
  - Async closures er stabile siden 1.85.
- **For regnskapsadapterne i N04 anbefales enum-dispatch.** Settet er lukket: Tripletex, PowerOffice, ReAi og SAF-T. Det gir nativ `async fn`, ingen boksing og full `Send`-kontroll.
- Alternativer:
  - `trait_variant::make(Send)` (0.1.3, fra rust-lang)
  - `async-trait` 0.1.92, der vi trenger `dyn`. Boksing per kall er ubetydelig mot et nettverkskall.
  - `dynosaur` 0.3.1
- **Paginering:** `fn posteringer(&self, q: Utvalg) -> BoxStream<'_, Result<Hovedbokslinje, KildeFeil>>` fra `futures` 0.3.34. Typen virker med `dyn` og er `Send`.
  - Bygg strømmen med `futures::stream::try_unfold` og en sidemarkør, eller med `async_stream::try_stream!`.
  - `async-stream` 0.3.6 er stabil og vedlikeholdt av tokio-rs, men lite endret siden 2024.
  - Saldomotoren konsumerer strømmen og holder bare akkumulatorer per konto og måned.

### 12. Fra N04: SAF-T-leser

**Versjon (Skatteetaten):**
- **1.40 er obligatorisk fra 1.1.2027.** 1.30 kan brukes til og med 31.12.2026, og eldre versjoner for tidligere år.
- Begge har navnerommet `urn:StandardAuditFile-Taxation-Financial:NO`, og Skatteetaten sier at 1.40 har «full backward compatibility».
- 1.40 legger til `NOKAmount`, `NOKTaxBase`, `Debit/CreditNOKTaxAmount`, `VirtualCurrencyType` og `SAFlongmonetaryType` (se §3).
- Leseren må godta 1.20, 1.30 og 1.40, og velger ut fra `AuditFileVersion`.
- N04 og N29 bør endres fra «SAF-T 1.30» til «SAF-T 1.30 og 1.40».

**Struktur (XSD 1.30):**
- `MasterFiles/GeneralLedgerAccounts/Account` har:
  - `AccountID`
  - `GroupingCategory` og `GroupingCode` (påkrevd)
  - `Opening` og `Closing` `Debit`/`CreditBalance`
- `AnalysisTypeTable` beskriver dimensjonene.
- `GeneralLedgerEntries` har `NumberOfEntries`, `TotalDebit` og `TotalCredit`. Under ligger `Journal/Transaction/Line` med:
  - `AccountID`
  - `Analysis*`, med `AnalysisType`, `AnalysisID` og `Debit` eller `CreditAnalysisAmount`
  - `CustomerID`, `SupplierID`, `Description`
  - `DebitAmount` eller `CreditAmount`, med `Amount` i NOK
- XSD-en har **ikke** eget ansattregister. Ansatte kan likevel finnes som leverandør (ansattreskontro), som analyse eller i `Description` [verifiseres]. N04 sier at filen inneholder ansatte, og det bør presiseres.

**Utkast til design [forslag]:**
1. **Strøm 1:** Les `Header` og `MasterFiles`. Bygg kontoplanen med grupperingskoder, og velg lønnskontoene fra D-A07Kontoregel.
2. **Strøm 2:** For hver `Transaction` leses deltreet med `read_to_end_into` og deserialiseres med quick-xml serde. Bare linjer på valgte kontoer beholdes.
3. **Minimering:**
   - Dropp `CustomerID` og `SupplierID`.
   - `Description` lagres ikke, eller lagres maskert.
   - Behold `Analysis` som dimensjon: type og id, med tekst fra `AnalysisTypeTable`.
   - Dropp de andre registrene.
4. **Kontrollsum:**
   - Tell antall linjer og summer debet og kredit over **hele** filen, også linjene vi kaster. Sammenlign med `NumberOfEntries`, `TotalDebit` og `TotalCredit`.
   - Kontroller IB + D − K = UB per valgt konto mot `Closing*Balance`.
5. **Råfilen:**
   - Lagres midlertidig og kryptert med `age`.
   - Slettes etter parsing.
   - D-Regnskapshenting får SHA-256, antall og summer.
6. **Pakkede filer og tegnsett:**
   - `zip` 9.1 leser zip-filer, men trenger `Seek`.
   - Andre tegnsett enn UTF-8 håndteres med `encoding_rs`.

## Konsekvens for Brutto

### Fase 1
- **A01–A06, T03 og T04:**
  - Stacken i §13 gjelder.
  - CI kjører `cargo-deny` med lisensene i §13, `clippy -D warnings` med `disallowed-methods` for `Decimal::round`/`round_dp` og `sqlx prepare --check`.
  - MSRV er minst 1.94 (sqlx 0.9).
- **F-MYN-01, M03 og M04:**
  - Egen modul med `Rs256Signer` og implementasjoner for den valgte KMS-en og en lokal PEM-nøkkel i dev.
  - JWT med `exp − iat` = 120 s. Maks er 180 s, så N06 er riktig, men grensen er 180.
  - Token-cache i moka med nøkkelen fra N06.
  - Skyvalget (H01) avgjør crate-en: Azure Norway East har Key Vault, mens Managed HSM [verifiseres].
- **F-MYN-21, M06, D05 og D07:**
  - Typer for avstemmingsrapporten genereres fra 1.0.2 med egne typer for `Beloep`, `BeloepSomHeltall`, `Desimaltall` og `DatoKlokkeslett`. Kallene håndskrives.
  - Ukjente felt fanges med `serde_ignored` og går til F-MYN-24.
  - Rådata lagres kryptert som `bytea` med hash. Det normaliserte laget ligger i tabeller med RLS. Det svarer på N03 spørsmål 4.
- **F-MYN-24:** RSS (`/rss/sbs/a-meldingen/` og `/rss/sbs/alle/`) pluss lenkediff og hash av regnearkene på SBS-siden. Kontrakttest mot TT02 hver natt (N39).
- **F-MYN-10 og F-KJO-18 (forberedes):** calamine-import av forretningsregler, kodeliste og inntektskombinasjoner til D-Regelpakke med SHA-256 og gyldig fra (N36).
- **F-MYN-38 og F-PER-24:** Ukentlig Klass-synk av 145, 7 og 426 til D-Kodeverk. Lag en sak når 145 har koder som mangler i 426.
- **F-REG-29 og F-REG-30:**
  - Adapterne lages som enum med nativ async og `BoxStream` for posteringer.
  - Tripletex-modellene genereres for de 85 skjemaene de fire kallene trenger, med `number` → `Decimal`.
  - SAF-T-reserven må lese **1.30 og 1.40**, fordi 1.40 er obligatorisk fra 1.1.2027.
  - Den må også minimere: ingen kunde- eller leverandør-id, og ingen beskrivelsestekst.
  - Den må kontrollere mot `NumberOfEntries`, `TotalDebit` og `TotalCredit`.
- **D02, D03 og F-SIK-11:**
  - sqlx 0.9 med `TenantTx` som eneste vei til databasen.
  - `ENABLE` og `FORCE` RLS, en applikasjonsrolle uten `BYPASSRLS`, og visninger med `security_invoker`.
  - Isolasjonstester med `#[sqlx::test]`.
- **D09, F-SIK-19 og F-SIK-20:**
  - AES-256-GCM på applikasjonsnivå med DEK per (tenant, dataklasse) og AAD.
  - Blind indeks med HMAC-SHA256 og en egen nøkkel.
  - Ikke pgcrypto.
- **D08:** Registreringstid på alt med et eget repolag. `WITHOUT OVERLAPS` (PG18) og `btree_gist` brukes når gyldighetstid kommer. Arbeidsforhold-ID lagres som `text COLLATE "C"`.
- **A04, M10 og F-BYR-15:** Egen kø med `aktiv_nokkel`, der nøkkelen er opplysningspliktig, og en felles token-bøtte per (system, legitimasjon). `governor` brukes bare lokalt.
- **D05 og K03:**
  - `brutto-penger` har avrundingsstrategi som data.
  - Toleransen for AGA (grunnlag × sats per sone mot `sumArbeidsgiveravgift`) bruker eksplisitt strategi, aldri `round()`.
- **F-RAP-03 og F-RAP-04:**
  - PDF av avstemmingsrapport og kontrolloppstilling lages med Typst som PDF/A-2b. Bruk 3b hvis JSON skal ligge vedlagt.
  - Lås med to hasher.
  - Excel med `rust_xlsxwriter` og CSV med `csv`.
- **F-SIK-36:** Egen opptaksmellomvare med vask og identitetsvakter. Avspilling i `wiremock`.

### MVP
- **F-KJO-42, F-KJO-44, F-POR-08 og F-REG-06:**
  - Lønnsslipp og lønnsjournal lages i Typst som PDF/A, med veraPDF i CI.
  - Lønnsslippen kan ha maskinlesbart vedlegg (PDF/A-3b).
  - Hash-lås ved godkjenning (F-MYN-11).
- **F-MYN-12, F-MYN-14 og F-MYN-20:**
  - A-melding-XML bygges med `quick-xml` og typer fra XSD (`xsd-parser`).
  - Validering mot XSD 2.3 med `xmllint` eller Xerces i CI. Versjon 2.4 kommer senere.
- **ADR-06:** Avrundingsreglene for prosenttrekk, feriepenger og AGA bekreftes faglig og legges i regelpakken. Største-rest-fordeling til regnskapet.
- **F-REG-18 og F-REG-19:** Skriveadapterne gjenbruker de genererte modellene og mellomvaren.
- **Jobbkøen** får lønnskjøring, betaling og innsending som tilstandsmaskiner (ADR-12). Kravene i §6 gjelder fortsatt.

### Senere
- **Automatisk nøkkelrotasjon** via Digdirs selvbetjenings-API, med virksomhetssertifikat (N06). `Rs256Signer` er uendret.
- **BYOK for store kunder:** Signer- og DEK-laget er allerede abstrahert.
- **XSD-validering i ren Rust** (`uppsala` og lignende) vurderes på nytt i 2027.
- **Innebygd dynamisk dispatch for async-traits** (mål 2026–2027) kan fjerne `async-trait`.
- **SAF-T-eksport fra Brutto** (N04 Senere) bruker samme typer og validering i CI.
- **F-PLA-01 og F-PLA-19:** Det offentlige API-et versjoneres med utoipa (OpenAPI 3.1, kanskje 3.2).

## Nye spørsmål

### Til backloggen
1. **Spike: Maskinporten-modulen med KMS-signering mot `test.maskinporten.no`.** Mål svartid per signering og token, feilkoder og `expires_in` i praksis. Prioritet 1, F1.
2. **Sky og KMS i Norge (H01).** Bekreft Azure Key Vault og Managed HSM i Norway East, GCP-regionen i Norge og Cloud KMS der, og Postgres 18 med `btree_gist` og PgBouncer hos den valgte leverandøren. Prioritet 1, F1.
3. **`arbitrary_precision` eller f64-stien.** Test begge mot opptak fra Tripletex, PowerOffice og ReAi. Se etter `flatten` og `untagged` i de genererte modellene. Prioritet 1, F1.
4. **Spike: jobbkø.** Egen kø mot `graphile_worker` (kjører navngitte køer jobbene én om gangen i Rust-porten?) og `apalis` 1.0. Krav: samtidighetsnøkkel, global bøtte, RLS og outbox. Prioritet 1, F1.
5. **Spike: typify og progenitor på Skatteetaten 1.0.2 og Tripletex-utdraget (85 skjemaer)** med erstatninger. Sjekk hva `date-time` og `allOf` blir. Prioritet 2, F1.
6. **SAF-T 1.30 og 1.40 i N29.** Testfiler fra Tripletex `/saft/exportSAFT`. Mål minne og tid på en stor fil, og sjekk om ansatte finnes som leverandør eller analyse. Prioritet 2, F1.
7. **PDF/A-løp.** Typst-mal, veraPDF i CI og valg mellom PDF/A-2b og 3b med vedlegg. Avklar med regnskapsfaglig om vedlegget har verdi for bokføringsgrunnlaget. Prioritet 2, F1 (rapporter) og MVP (lønnsslipp).
8. **Avrundingsregler.** Prosenttrekk, AGA og feriepenger, slått opp i forskrift og hos Skatteetaten. Gi en tabell over `RoundingStrategy` per regel. Prioritet 2, MVP (toleranse i F1).
9. **Ledende nuller i regnearkene.** Sjekk om kodene i forretningsreglene og kodelisten R1 2026 er lagret som tekst. Prioritet 2, F1. Slås sammen med N36.
10. **XSD-validering for a-melding.** Velg verktøy for CI, og avgjør om det trengs validering i drift. Følg med på vedlikeholdet av libxml2. Prioritet 3, MVP.
11. **Lisenspolicy i `cargo-deny`.** MPL-2.0, ISC, BSD-2 og unntak for «non-standard». Kan Regnskap Norges standardkontoer (lisensmerknad i SAF-T-repoet) brukes i malen? Slås sammen med N23 spørsmål 4. Prioritet 3, F1.

### Til Peter og Sander
1. Godtar dere at vi bygger JWS-en selv (ca. 60 linjer) med signering i KMS, og bruker `jsonwebtoken` bare til å verifisere i tester?
2. Hvilken sky og KMS velger vi (H01)? Det avgjør hvilken SDK-crate `Rs256Signer` bruker først.
3. Skal `serde_json/arbitrary_precision` slås på i hele workspace fra dag én? Alternativet er f64-stien med en kontroll på maks 15 sifre. Første valg forbyr `flatten` og `untagged` på typer med tall.
4. Sjekker vi inn generert kode (`cargo-typify`, egen crate per system), eller bruker vi `build.rs`? Forslaget er å sjekke inn, for lesbar diff og raskere bygg.
5. Enum-dispatch for regnskapsadapterne, eller `dyn` med `async-trait`? Forslaget er enum, fordi settet er lukket.
6. Egen jobbkø (1–2 uker) eller `graphile_worker`? Og hvordan skal den globale token-bøtten deles mellom flere arbeidsnoder?
7. Rådata lagres kryptert som `bytea` og kan ikke spørres med JSONB. Godtar dere at kontrollene bare kjører på det normaliserte laget?
8. Skal `clippy.toml` forby `Decimal::round` og `round_dp`, og `clippy::float_arithmetic` slås på i crate-ene for penger og regler?
9. Hva er MSRV-policyen? sqlx 0.9 krever 1.94. Følger vi siste stabile, eller låser vi og oppgraderer hvert kvartal?
10. Typst til all PDF: rapporter i fase 1, og lønnsslipp og lønnsjournal i MVP. Eller vil dere ha HTML→PDF (Gotenberg) for at frontend og PDF skal se like ut?
